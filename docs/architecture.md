# Архитектура DnD Memory

## 1. Что это

Справочник настольной сессии D&D: герои партии, встреченные персонажи, локации и
найденные предметы с краткими описаниями, пересказы сессий и живая навигация по
упоминаниям (наименование в тексте — гиперссылка на карточку объекта).

Три части:

```
                    ┌──────────────────────────┐
   Android (Java)   │  Сервер приложений        │   Веб-версия (PWA)
   Room + WorkManager│  Java 11 / Spring Boot   │   Vue 3 + IndexedDB
   Retrofit         │  PostgreSQL 15 + Flyway   │   Service Worker
                    │  JWT, REST, change-log    │
                    └───────────┬──────────────┘
                                │
                      nginx (TLS, статика веба)
                                │
                   Docker: контуры test и prod
```

## 2. Ключевые решения

| Решение | Почему так |
|---|---|
| Четыре класса (герои, персонажи, локации, предметы) со своими таблицами и общей частью в `@MappedSuperclass` | Новое поле типа не затрагивает остальные, а ссылки, поиск и синхронизация остаются общими |
| Синхронизация по журналу ревизий кампании (`change_log`) | Простая и предсказуемая: клиент помнит одну цифру `lastPulledRevision` |
| Идентификаторы генерирует клиент (UUID) | Офлайн-созданная запись сразу имеет окончательный id, конфликтов «временных id» нет |
| Дубли ловятся по ключу сопоставления класса (имя, у персонажа — имя и раса) | Правило задано методом самого класса и меняется одной строкой |
| Роли + привязка к герою (`linkedHeroId`) | Требование «редактор как герой / как мастер / просмотр как гость» |
| Черновики пересказов только локально | Прямое требование: черновик не отправляется на сервер |
| Last-write-wins по `updatedAt` на уровне объекта | Простая модель для справочника; конфликты не теряются, а показываются пользователю |
| Разметка `[[Имя]]` в тексте | Совместимо с Obsidian, легко парсится всеми тремя клиентами |
| Java 11 на сервере | Требование заказчика; Spring Boot 2.7 — последняя ветка, работающая на 11 |
| Один Docker-хост, два контура (`test`, `prod`) | Требование «тестовая для меня и рабочая»: разные тома, порты, домены, базы |

## 3. Сервер

* Spring Boot 2.7.18, Java 11, Maven, упаковка в тонкий jar.
* PostgreSQL 15 + Flyway (`server/src/main/resources/db/migration`).
* Слои: `domain` (JPA-сущности), `repo`, `service`, `web` (контроллеры + DTO),
  `security` (JWT и права доступа), `config`.
* Вход — только логин и пароль; внешних провайдеров нет. Сброс пароля без SMTP:
  одноразовая ссылка пишется в лог и видна в админ-панели по `DND_ADMIN_TOKEN`.
* Пароли — BCrypt. Access-токен JWT HS256 (15 мин), refresh — случайная строка в БД с ротацией (30 дней для веба, 365 для приложения).
* Файлы — локальный том Docker (`/var/lib/dnd-memory/files`), раздача через `/api/files/{id}`.
* Фоновые задачи Spring `@Scheduled`: компактация журнала синхронизации, очистка
  просроченных приглашений, refresh-токенов и запросов сброса пароля.
* Наблюдаемость: `/api/health` (используется в `HEALTHCHECK` контейнера),
  структурированные логи в stdout, `X-Request-Id`.

## 4. Веб-версия

* Vue 3 + TypeScript + Vite, Pinia, vue-router, `idb` (IndexedDB), `vite-plugin-pwa`.
* Тот же офлайн-первый алгоритм, что в Android: локальная база в IndexedDB,
  очередь `pending_changes`, push → pull.
* Вкладки «Герои», «Персонажи», «Локации», «Предметы», «Пересказы», «Участники»
  и общий поиск по кампании (по локальной базе — работает без сети).
* Разметка описаний — markdown + `[[ссылки]]`, рендер с подсветкой ссылок.
* QR: генерация — библиотека `qrcode`, сканирование — камера через `BarcodeDetector`
  с запасным `jsqr`.
* Сборка — статические файлы, раздаются nginx в том же контейнере/compose.

## 5. Android-приложение

* Java 11-совместимый синтаксис, `minSdk 24`, `targetSdk 34`, AGP 8.x, Gradle 8.x.
* Room (локальная база), Retrofit + OkHttp (сеть), WorkManager (фоновой синхронизацией),
  DataStore (токены), ZXing embedded (сканирование QR), Material Components, ViewBinding.
* Экраны: вход/регистрация, список кампаний, кампания с вкладками, карточка объекта
  (просмотр/правка), пересказы (черновик/публикация), участники, приглашения с QR,
  поиск, настройки синхронизации.
* Архитектура MVVM: `Activity/Fragment → ViewModel (LiveData) → Repository → Room/Retrofit`.
* Сеть недоступна — интерфейс работает полностью, статус синхронизации виден в шапке.

## 6. Развёртывание

* `docker/compose.test.yml` — тестовый контур: порт 8081, том `dnd-test-*`, отдельная БД.
* `docker/compose.prod.yml` — рабочий контур: порт 8080, том `dnd-prod-*`, TLS через nginx.
* Оба контура поднимаются на одном сервере независимыми compose-проектами
  (`-p dnd-test`, `-p dnd-prod`), поэтому не пересекаются.
* `scripts/deploy.sh` — пересборка и подъём выбранного контура, `scripts/backup.sh` — дамп БД.
* Подробности — `deployment.md`.

## 7. Чего в первой версии нет (осознанно)

* Push-уведомлений между участниками.
* Скрытых «заметок мастера» — вся кампания видна всем участникам.
* Слияния полей при конфликте (только «кто позже, тот и прав»).
* Загрузки файлов в офлайне: изображение прикрепляется при наличии сети.
* Полнотекстового поиска PostgreSQL (`tsvector`): для объёмов кампании хватает
  `ILIKE`; при росте данных перейти на `pg_trgm` — точка расширения уже в `SearchService`.
