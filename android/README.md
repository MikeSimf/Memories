# DnD Memory — Android-приложение

Справочник настольной сессии D&D: герои партии, встреченные персонажи, локации,
предметы, пересказы сессий и живая навигация по упоминаниям (`[[Имя]]` — ссылка на
карточку объекта). Приложение офлайн-первое: интерфейс работает по локальной базе,
сеть нужна только для синхронизации.

Контракт с сервером: `../docs/api.md` (разделы 3, 4, 5, 6, 9), `../docs/sync.md`,
`../docs/roles.md`. Решения второй версии — `../docs/redesign-v2.md`.

## 1. Как открыть и собрать

```bash
# Android Studio: File → Open → выбрать каталог android/
# либо из командной строки:
./gradlew :app:assembleDebug
```

Полная команда сборки (так проверялся проект в этом окружении):

```bash
cd android
export JAVA_HOME=$(ls -d /data/external/tools/jdk-17* | head -1)
export ANDROID_HOME=/data/external/tools/android-sdk
export GRADLE_USER_HOME=/data/external/tools/gradle-home

./gradlew assembleDebug --no-daemon --max-workers=1 \
  -Dorg.gradle.jvmargs="-Xmx1024m -XX:MaxMetaspaceSize=512m" -Dorg.gradle.parallel=false

./gradlew assembleRelease --no-daemon --max-workers=1 \
  -Dorg.gradle.jvmargs="-Xmx1024m -XX:MaxMetaspaceSize=512m" -Dorg.gradle.parallel=false
```

Проверка согласованности ссылок «код → ресурсы» без сборки:

```bash
node /data/external/dnd-memory/scripts/check-android.mjs
```

Требования:

| Что | Версия |
|---|---|
| Android Studio | Ladybug (2024.2) или новее |
| JDK | 17 (Android Studio использует встроенный JBR 17) |
| Android Gradle Plugin | 8.2.2 |
| Gradle | 8.5 (wrapper в комплекте) |
| compileSdk / targetSdk | 34 |
| minSdk | 24 |
| Build Tools | 34.0.0 (ставится Android Studio) |

Исходный код — **только Java 11**, без Kotlin, Hilt и Dagger (всё внедрение
зависимостей — вручную в `AppContainer`), без `kapt`/`annotationProcessor` кроме
Room.

## 2. Адрес сервера

Базовый адрес берётся из `BuildConfig.DND_SERVER_URL` и задаётся в
`gradle.properties`:

```properties
DND_SERVER_URL=http://10.0.2.2:8080/
```

* `10.0.2.2` — адрес хост-машины из эмулятора Android.
* Для реального устройства укажите адрес контура, например
  `DND_SERVER_URL=https://dnd.example.com/`.
* Значение обязано заканчиваться на `/` (скрипт добавит его сам, если забыли).
* Открытый HTTP разрешён только для `10.0.2.2`, `localhost` и `127.0.0.1`
  (`app/src/main/res/xml/network_security_config.xml`).

Другое поле `BuildConfig` — `DEEP_LINK_SCHEME` (`dndmemory`), схема deep link
приглашений.

## 3. Вход и регистрация

Экран `AuthActivity` — две вкладки: **«Вход»** и **«Регистрация»**. Основной и
единственный способ входа — логин и пароль: внешних провайдеров и регистрации
устройства по QR больше нет (`docs/redesign-v2.md`, раздел 1).

**Вход** — логин и пароль, регистр логина не важен (`POST /api/auth/login`).
Приложение передаёт `platform: "android"` (`AuthRepository.PLATFORM_ANDROID`),
поэтому refresh-токен выдаётся на 365 дней вместо 30, а access-токен живёт
15 минут.

**Регистрация** — имя, логин (3–32 символа из `a–z`, `0–9`, `_`, `.`, `-`), почта
(обязательна и уникальна — на неё приходит ссылка сброса пароля) и пароль от
8 символов → `POST /api/auth/register` с тем же `platform` и, если он есть,
`inviteToken`. Ответ содержит токены и профиль; `SessionStore` сохраняет
access- и refresh-токен, логин, имя, почту, телефон и признак пароля.

Сессия живёт на устройстве, поэтому логин и пароль вводятся один раз.
`AuthInterceptor` подставляет `Authorization: Bearer <accessToken>`, а
`TokenAuthenticator` при `401` один раз вызывает `POST /api/auth/refresh`
(refresh-токен ротируется) и повторяет запрос — повторный `401` обновление не
зацикливает. Если refresh отвергнут (`401`/`403`/`404`), `SessionStore.markRevoked`
очищает сессию и открывается экран входа с пояснением «Сессия истекла — войдите
заново логином и паролем». Локальные данные (кампании, объекты в Room, черновики
пересказов) при этом **не удаляются**, а сетевая ошибка сессию не сбрасывает —
обрыв выяснится при первой удачной попытке.

Ссылки на экране входа: **«Забыли пароль?»** → `PasswordResetActivity`;
**«У меня есть приглашение»** → ввод кода приглашения вручную.

### Вход по приглашению

QR от мастера содержит deep link `dndmemory://join?token=…`; код можно ввести и
вручную. Сканирует `ScanActivity` (ZXing embedded; разрешение на камеру
запрашивается на входе в этот экран).

`InviteAcceptActivity` сначала берёт публичный предпросмотр
`GET /api/invites/{token}` — кампания, роль, привязанный герой, срок:

| Есть сессия | Нет сессии |
|---|---|
| кнопка **«Принять»** → `POST /api/invites/{token}/accept` | кнопки **«Зарегистрироваться»** и **«Войти»** → `AuthActivity` |

Регистрация передаёт `inviteToken` в `POST /api/auth/register` — пользователь
создаётся и сразу становится участником кампании; после обычного входа приглашение
принимается запросом `accept`. Затем показывается «Вы присоединились к кампании»
и открывается кампания.

Приглашение **строго одноразовое** (`maxUses = 1`). Повторное, просроченное или
отозванное приглашение даёт `409 invite_invalid` и текст «Приглашение уже
использовано или просрочено» (`docs/api.md`, раздел 5).

Deep link ровно один: `dndmemory://join?token=…` — `InviteAcceptActivity`.

## 5. Кампания: три вкладки и быстрый фильтр

В экране кампании ровно **три вкладки**:

| Вкладка | Классы объектов | Локальная база |
|---|---|---|
| Персонажи | `HERO`, `CHARACTER` | `kind IN ('HERO','CHARACTER')` |
| Локации | `LOCATION` | `kind IN ('LOCATION')` |
| Предметы | `ITEM` | `kind IN ('ITEM')` |

Герои и НПС живут в одной вкладке и различаются значком и подписью типа в строке,
а не разделением на разные вкладки. У каждого класса свой REST-эндпоинт, поэтому
вкладка «Персонажи» при обновлении опрашивает `/heroes` и `/characters`.

Пересказы, Участники и Приглашения вынесены из вкладок в пункты меню шапки
кампании (`menu/menu_campaign.xml`, без дублирования): «Пересказы» открывает
`RetellingListActivity`, «Участники» — `MembersActivity`, «Приглашения» —
`InviteActivity`; там же поиск и обновление.

Вверху каждой вкладки — поле **быстрого фильтра**:

* фильтрует список прямо во время набора, задержка 200 мс (`Handler.postDelayed`);
* без учёта регистра по названию и описанию, а у персонажа — ещё и по расе с
  кратким описанием;
* считает совпадения в фоновом потоке (`AppExecutors.io`), устаревшие проходы
  отбрасываются по номеру поколения;
* список обновляется через `ListAdapter` + `DiffUtil`, адаптер не пересоздаётся;
* показывает «Найдено: N» и кнопку «Очистить фильтр»; пустые состояния различают
  «здесь пусто» и «фильтр ничего не нашёл»;
* работает офлайн по локальной базе и не мешает поиску по кампании
  (`SearchActivity`, чипы «Всё» / «Персонажи» / отдельные виды / «Пересказы»).

## 6. Объекты: четыре класса

Вместо прежней общей сущности с `attrs` — четыре класса с настоящими полями
(`docs/api.md`, раздел 6). В локальной базе они лежат в одной таблице `entities`
с дискриминатором `kind`, но у каждого класса своя форма DTO и свой набор
эндпоинтов (`/heroes`, `/characters`, `/locations`, `/items`); общего
`/api/campaigns/{id}/entities` больше нет.

| Класс | Свои поля | Кто создаёт, правит и удаляет |
|---|---|---|
| **Герой** (`HeroDto`) | `race`, `klass`, `playerUserId` / `playerName` (кто отыгрывает) и `items` — котомка (`name`, `quantity`, `notes`, `itemId` заполнен, если название нашлось среди предметов кампании) | **только владелец** кампании (`hero.write`) |
| **Персонаж** (НПС, `CharacterDto`) | `race`, `shortDescription` | владелец, редактор-мастер, редактор-герой (`entity.write`) |
| **Локация** (`LocationDto`) | своих полей нет | то же (`entity.write`) |
| **Предмет** (`ItemDto`) | `ownerName` — владелец «как написано в мире», и необязательная ссылка `ownerHeroId` **или** `ownerCharacterId` (не более одной) | то же (`entity.write`) |

Общие поля ответа: `id`, `campaignId`, `name`, `description`, `imageFileId`,
`links`, `createdBy`/`createdByName`, `updatedBy`/`updatedByName`, `revision`,
`createdAt`, `updatedAt`, `deleted`. `links` заполняет сервер разбором `[[…]]`;
офлайн приложение разрешает имена по своей базе теми же правилами.

Карточка объекта показывает настоящие поля: у героя — раса, класс, игрок и
котомка; у персонажа — раса и краткое описание; у предмета — владелец со ссылкой.
`imageFileId` в DTO есть, но интерфейса прикрепления картинки нет: `POST /api/files`
объявлен в `ApiService` и не используется.

## 7. Внешний вид

* Палитра: тёплый «пергамент» в светлой теме и «подземелье» в тёмной, акценты
  золото/бронза (`res/values/colors.xml`, `res/values-night/colors.xml`).
* Тема одна — `Theme.DnDMemory` (`res/values/themes.xml`) на базе
  `Theme.Material3.DayNight.NoActionBar`; цвета берутся по именам, поэтому светлая
  и тёмная темы отличаются только файлом цветов.
* Стили `Widget.DnDMemory.Card` (скругление 14 dp, тонкая граница вместо тени),
  `Widget.DnDMemory.Toolbar`, `Widget.DnDMemory.Filter`,
  `Widget.DnDMemory.PrimaryButton`.
* Только векторные иконки (drawable), системные шрифты, никаких тяжёлых анимаций,
  градиентов и больших картинок — приоритет скорость и читаемость.
* Все строки — в `strings.xml` (русский), цвета — в `colors.xml`,
  темы — в `themes.xml`.

## 8. Профиль и настройки

Экран `SettingsActivity` показывает имя, логин (только для чтения), почту и
телефон и позволяет:

* изменить имя, почту и телефон — `PATCH /api/me`
  (`{ displayName, email, phone }`); **почта обязательна** — это адрес для сброса
  пароля, телефон необязателен; сервер нормализует телефон к `+7XXXXXXXXXX`,
  занятая почта и телефон показываются понятными текстами (`email_taken`,
  `phone_taken`), пустое поле телефона очищает значение;
* сменить пароль — `POST /api/me/password`; текущий пароль обязателен (пароль есть
  всегда, потому что вход только по паролю), новый — не короче 8 символов,
  вводится дважды;
* посмотреть адрес сервера, версию, время последней синхронизации;
* настроить «синхронизировать только по Wi-Fi», запустить синхронизацию сейчас
  или полную перезагрузку кампании;
* выйти из аккаунта — с предупреждением про локальные данные и неотправленные
  черновики.

Отдельный экран **сброса пароля** (`PasswordResetActivity`) просит почту и
вызывает `POST /api/auth/password-reset/request`. Ответ всегда `202` — по нему
нельзя узнать, есть ли такой адрес. Почтовый сервер не настроен: одноразовая
ссылка пишется в лог сервера и видна администратору
(`GET /api/admin/password-resets`), так и написано на экране. Подтверждение по
ссылке делает веб-версия — отдельного экрана в приложении нет.

## 9. Приглашения

Экран `InviteActivity` (право `invite.create`, см. `docs/roles.md`) — только
приглашения, раздела «Устройства» и отзыва доступа больше нет:

* **Создание QR** — роль, необязательная привязка к герою и срок (по умолчанию
  168 ч = 7 дней) → `POST /api/campaigns/{id}/invites`. В ответ приходят
  `qrPngBase64`, код и `deepLink`; QR показывается поверх списка, код и ссылку
  можно передать вручную.
* **Список** — `GET /api/campaigns/{id}/invites`: код, роль, срок,
  использование (`uses`/`maxUses`, всегда 1). Нажатие на строку снова показывает
  QR.
* **Отзыв** — `DELETE /api/campaigns/{id}/invites/{inviteId}` с подтверждением.
* Кнопка сканера открывает `ScanActivity`, чтобы принять чужое приглашение с
  этого же устройства.

Приглашение строго одноразовое: `maxUses` всегда 1 и в запросе не передаётся.
Принятие помечает его использованным (`valid: false`), повтор даёт
`409 invite_invalid`.

## 10. Офлайн-режим и синхронизация

Локальная база (Room) — единственный источник данных для интерфейса. Сеть меняет
её двумя путями: прямыми запросами (список кампаний, участники, приглашения,
объекты по классам) и движком синхронизации `SyncEngine`.

Правки объектов и пересказов всегда локальные:

1. запись сразу попадает в Room, объект помечается `dirty = 1`;
2. в `pending_changes` добавляется запись с `base_revision` объекта;
3. `SyncScheduler` ставит отложенный воркер (debounce 3 с).

`SyncEngine` выполняет цикл из `docs/sync.md` строго в порядке **push → pull**:

* `objectType` в журнале — **конкретный класс**: `HERO`, `CHARACTER`, `LOCATION`,
  `ITEM`, `RETELLING`, `CAMPAIGN`, `MEMBER`; `payload` — объект в форме DTO своего
  класса. Общего `ENTITY` больше нет: на него сервер отвечает `REJECTED` с
  `unsupported_type`;
* `POST /api/campaigns/{id}/sync/changes` — очередь уходит по возрастанию `seq`,
  каждая правка несёт `clientChangeId` (ключ идемпотентности) и `clientId`
  установки;
* `APPLIED` / `CONFLICT_RESOLVED` — правка снимается с очереди, объект помечается
  чистым; `REJECTED` — снимается с очереди, состояние сервера сохраняется в
  `conflict_json`, интерфейс показывает «есть расхождение» и предлагает выбрать
  свою версию или серверную;
* если объект с тем же ключом сопоставления в кампании уже есть, дубль не
  создаётся: правки ложатся в существующий, ответ получает `CONFLICT_RESOLVED` и
  `conflict.reason = "matched_by_name"` (у персонажа —
  `matched_by_name_and_race`). Ключ: у героя, локации и предмета — имя, у
  персонажа — имя и раса;
* `GET /api/campaigns/{id}/sync/changes?since=…` — журнал применяется к базе,
  при `hasMore = true` запрос повторяется;
* `410 resync_required` (журнал скомпактился) — полная перезагрузка через
  `GET /sync/snapshot` с курсорами.

Черновики пересказов **не покидают устройство**: пока пользователь не нажал
«Опубликовать», текст живёт в таблице `retelling_drafts` и не попадает ни в
`pending_changes`, ни в push.

Ссылки `[[Имя]]`, `[[Имя|подпись]]`, `[[#uuid|подпись]]` разрешаются **по
локальной базе** (те же правила, что у сервера) по всем четырём классам.

Когда запускается синхронизация:

| Событие | Реализация |
|---|---|
| Старт приложения | `App.onCreate` → `SyncEngine.syncAll()` в фоне |
| Появление сети | `WorkManager`, `NetworkType.CONNECTED` |
| Локальная правка | отложенный воркер, debounce 3 с |
| Вручную | pull-to-refresh в списках, «Синхронизировать сейчас» в настройках |
| Периодически | периодический воркер раз в 15 минут |

## 11. Роли и права

Права приходят от сервера в `myPermissions` и проверяются на клиенте только для
того, чтобы не показывать недоступные действия (`ui/common/Rights.java`,
матрица — `../docs/roles.md`). Решение всё равно принимает сервер.

* героев создаёт, правит и удаляет **только владелец** (`hero.write`);
* персонажей, локации и предметы — владелец, редактор-мастер и редактор-герой
  (`entity.write`); вкладка «Персонажи» показывает кнопку добавления, если
  доступен хотя бы один из классов;
* читают все участники, включая гостя (`entity.read`);
* участники и приглашения — `members.manage` / `invite.create`.

## 12. Тестовый обход

1. Запустить сервер (контур `test`, порт 8081) и указать его в `DND_SERVER_URL`.
2. Собрать и установить приложение. Первый запуск без сессии — экран входа:
   зарегистрироваться (логин, почта, пароль, имя) или войти.
3. В кампании выпустить приглашение (Приглашения → «Создать»), отсканировать QR
   вторым телефоном: приложение предложит зарегистрироваться или войти; после
   регистрации с `inviteToken` игрок сразу оказывается в кампании.
4. Создать героя (владелец) и персонажа — оба видны во вкладке «Персонажи» с
   разными подписями; ввести в фильтр часть имени, а для персонажа — расу: список
   сужается, показывается «Найдено: N».
5. Включить авиарежим, поправить объект и создать пересказ-черновик — интерфейс
   продолжает работать, в шапке «Нет сети — работаем офлайн».
6. Выключить авиарежим, дождаться синхронизации — правки уходят на сервер,
   черновик остаётся на устройстве до нажатия «Опубликовать».
7. Повторно открыть тот же QR — «Приглашение уже использовано или просрочено»
   (`409 invite_invalid`).
8. «Забыли пароль?» → указать почту: экран сообщает, что ссылка передана
   администратору (в логе сервера строка `СБРОС ПАРОЛЯ: …`).

## 13. Известные отклонения и точки внимания

* **Хранилище токенов.** В `app/build.gradle` объявлена зависимость
  `androidx.datastore:datastore-preferences:1.0.0`, но `SessionStore` использует
  закрытый файл `SharedPreferences`. Причина: Java-API DataStore работает только
  через coroutine-interop (`BuildersKt.runBlocking`, `FlowKt.first`), который
  нельзя проверить без компилятора, а доступ к токену нужен синхронно в
  `AuthInterceptor`. Перевести хранилище на DataStore можно, заменив реализацию
  одного класса.
* **Release-сборка не подписана.** В `app/build.gradle` нет `signingConfigs`,
  поэтому `assembleRelease` даёт неподписанный APK. Для установки на устройство
  ключ задаётся вручную (см. раздел 14).

## 14. Проверка сборки

Сборка прогнана по-настоящему (JDK 17, Android SDK 34, Gradle 8.5 из wrapper):

```bash
cd android
export JAVA_HOME=$(ls -d /data/external/tools/jdk-17* | head -1)
export ANDROID_HOME=/data/external/tools/android-sdk
export GRADLE_USER_HOME=/data/external/tools/gradle-home

./gradlew assembleDebug   --no-daemon --max-workers=1 -Dorg.gradle.jvmargs="-Xmx1024m -XX:MaxMetaspaceSize=512m" -Dorg.gradle.parallel=false
./gradlew assembleRelease --no-daemon --max-workers=1 -Dorg.gradle.jvmargs="-Xmx1024m -XX:MaxMetaspaceSize=512m" -Dorg.gradle.parallel=false

node /data/external/dnd-memory/scripts/check-android.mjs
```

Результат: `BUILD SUCCESSFUL` для обоих вариантов, `check-android` — без
расхождений («Android-проект согласован»).

Для установки на устройство соберите release с ключом:

```bash
./gradlew assembleRelease -Pandroid.injected.signing.store.file=... # или настройте signingConfigs
```
