# DnD Memory — Android-приложение

Справочник настольной сессии D&D: герои партии, встреченные персонажи, локации,
предметы, пересказы сессий и живая навигация по упоминаниям (`[[Имя]]` — ссылка на
карточку объекта). Приложение офлайн-первое: интерфейс работает по локальной базе,
сеть нужна только для синхронизации.

Контракт с сервером: `../docs/api.md` (особенно разделы 3, 3.1, 5, 6),
`../docs/sync.md`, `../docs/roles.md`.

## 1. Как открыть и собрать

```bash
# Android Studio: File → Open → выбрать каталог android/
# либо из командной строки:
./gradlew :app:assembleDebug
```

Полная команда сборки (так проверялся проект в этом окружении):

```bash
cd android
export JAVA_HOME=$(ls -d /data/external/tools/jdk-17* | head -1)
export ANDROID_HOME=/data/external/tools/android-sdk
export GRADLE_USER_HOME=/data/external/tools/gradle-home

./gradlew assembleDebug --no-daemon --max-workers=1 \
  -Dorg.gradle.jvmargs="-Xmx1024m -XX:MaxMetaspaceSize=512m" -Dorg.gradle.parallel=false

./gradlew assembleRelease --no-daemon --max-workers=1 \
  -Dorg.gradle.jvmargs="-Xmx1024m -XX:MaxMetaspaceSize=512m" -Dorg.gradle.parallel=false
```

Проверка согласованности ссылок «код → ресурсы» без сборки:

```bash
node ../scripts/check-android.mjs
```

Требования:

| Что | Версия |
|---|---|
| Android Studio | Ladybug (2024.2) или новее |
| JDK | 17 (Android Studio использует встроенный JBR 17) |
| Android Gradle Plugin | 8.2.2 |
| Gradle | 8.5 (wrapper в комплекте) |
| compileSdk / targetSdk | 34 |
| minSdk | 24 |
| Build Tools | 34.0.0 (ставится Android Studio) |

Исходный код — **только Java 11**, без Kotlin, Hilt и Dagger (всё внедрение
зависимостей — вручную в `AppContainer`), без `kapt`/`annotationProcessor` кроме
Room.

## 2. Адрес сервера

Базовый адрес берётся из `BuildConfig.DND_SERVER_URL` и задаётся в
`gradle.properties`:

```properties
DND_SERVER_URL=http://10.0.2.2:8080/
```

* `10.0.2.2` — адрес хост-машины из эмулятора Android.
* Для реального устройства укажите адрес контура, например
  `DND_SERVER_URL=https://dnd.example.com/`.
* Значение обязано заканчиваться на `/` (скрипт добавит его сам, если забыли).
* Открытый HTTP разрешён только для `10.0.2.2`, `localhost` и `127.0.0.1`
  (`app/src/main/res/xml/network_security_config.xml`).

Другие поля `BuildConfig`: `OAUTH_REDIRECT_URI` (`dndmemory://oauth`) и
`DEEP_LINK_SCHEME` (`dndmemory`).

## 3. Вход: QR-код устройства — основной способ

Приложение **не начинается с формы пароля**. Порядок такой:

1. Первый запуск без сохранённой сессии → `EnrollActivity`:
   «Отсканируйте QR-код от мастера», большая кнопка **«Сканировать QR»**
   (ZXing embedded, `ScanActivity`) и поле **«или введите код вручную»**
   (например `7F3K9Q2M`).
2. Отправка — `POST /api/devices/enroll` с телом
   `{ "token": …, "label": "Xiaomi M2101K6G", "platform": "android" }`
   (`label` — `Build.MANUFACTURER + " " + Build.MODEL`, `util/DeviceInfo.java`).
3. Успех → `SessionStore.saveEnrollment` сохраняет `accessToken`, `refreshToken`,
   `deviceId` (серверная запись устройства), профиль, почту, телефон и признак
   `hasPassword`; показывается приветствие «Вы вошли как <имя>» и открывается
   список кампаний.
4. Ошибка → понятный текст: просроченный или уже использованный код
   (`409 invite_invalid`), нет сети, чужой тип кода.

Форма входа по почте/паролю и OAuth осталась вторичным вариантом: на экране QR
это ссылка **«У меня уже есть аккаунт»** (`AuthActivity`).

Аккаунт, созданный по QR, живёт без пароля. В профиле (раздел 7) человек указывает
почту или телефон и задаёт пароль — после этого работает вход в веб-версию.

### Два разных QR и два deep link

| | Приглашение участника | Регистрация устройства |
|---|---|---|
| Режим | `mode: "MEMBER"` | `mode: "DEVICE"` |
| Кто выпускает | `POST /api/campaigns/{id}/invites` | `POST /api/campaigns/{id}/devices/enrollments` |
| Как принимается | `POST /api/invites/{token}/accept` (нужен вход) | `POST /api/devices/enroll` (без входа) |

Решение клиента — как в `docs/api.md`, раздел 3.1: **есть сессия → `accept`,
сессии нет → `enroll`**. Экран `InviteAcceptActivity` сначала берёт публичный
предпросмотр `GET /api/invites/{token}`: если `mode: DEVICE`, человека сразу ведут
на экран регистрации устройства; если это приглашение участника, а сессии нет,
приложение пробует `enroll` и, получив отказ, предлагает войти или
зарегистрироваться (после входа приглашение принимается само).

* `dndmemory://join?token=…` — `InviteAcceptActivity` (приглашение или QR устройства).
* `dndmemory://oauth` — `OAuthCallbackActivity` (возврат из Custom Tab; если вход
  начат со ссылки-приглашения, после входа пользователь возвращается на неё).

### Обновление токена и отзыв доступа

* `TokenAuthenticator`: на `401` один раз вызывается `POST /api/auth/refresh`
  (refresh-токен ротируется), запрос повторяется **один раз** — повторный `401`
  не зацикливает обновление.
* Если сервер ответил, что устройство **отозвано** («Устройство отозвано
  администратором»), `SessionStore.markRevoked` очищает только сессию и
  `deviceId`, а `App` открывает экран QR с сообщением «Доступ отозван мастером —
  попросите новый QR-код».
* Локальные данные (кампании, объекты в Room, черновики пересказов) при отзыве
  **не удаляются**: после нового QR-кода они пригодятся. Сетевая ошибка и офлайн
  сессию не сбрасывают — отзыв выяснится при первой удачной попытке
  синхронизации.

## 5. Кампания: три вкладки и быстрый фильтр

В экране кампании ровно **три вкладки**:

| Вкладка | Запрос | Локальная база |
|---|---|---|
| Персонажи | `?types=HERO,NPC` | `type IN ('HERO','NPC')` |
| Локации | `?types=LOCATION` | `type IN ('LOCATION')` |
| Предметы | `?types=ITEM` | `type IN ('ITEM')` |

Герои и НПС живут в одной вкладке и различаются значком и подписью типа в строке,
а не разделением на разные вкладки.

Пересказы, Участники и Приглашения вынесены из вкладок в пункты меню шапки
кампании (`menu/menu_campaign.xml`, без дублирования): «Пересказы» открывает
`RetellingListActivity`, «Участники» — `MembersActivity`, «Приглашения» —
`InviteActivity`. Функциональность этих экранов сохранена полностью.

Вверху каждой вкладки — поле **быстрого фильтра**:

* фильтрует список прямо во время набора, задержка 200 мс (`Handler.postDelayed`);
* без учёта регистра по названию, краткому описанию, описанию и меткам;
* считает совпадения в фоновом потоке (`AppExecutors.io`), устаревшие проходы
  отбрасываются по номеру поколения;
* список обновляется через `ListAdapter` + `DiffUtil`, адаптер не пересоздаётся;
* показывает «Найдено: N» и кнопку «Очистить фильтр»; пустые состояния различают
  «здесь пусто» и «фильтр ничего не нашёл»;
* работает офлайн по локальной базе и не мешает поиску по кампании
  (`SearchActivity`, чипы «Всё» / «Персонажи» / отдельные виды / «Пересказы»).

## 6. Внешний вид

* Палитра: тёплый «пергамент» в светлой теме и «подземелье» в тёмной, акценты
  золото/бронза (`res/values/colors.xml`, `res/values-night/colors.xml`).
* Тема одна — `Theme.DnDMemory` (`res/values/themes.xml`) на базе
  `Theme.Material3.DayNight.NoActionBar`; цвета берутся по именам, поэтому светлая
  и тёмная темы отличаются только файлом цветов.
* Стили `Widget.DnDMemory.Card` (скругление 14 dp, тонкая граница вместо тени),
  `Widget.DnDMemory.Toolbar`, `Widget.DnDMemory.Filter`,
  `Widget.DnDMemory.PrimaryButton`.
* Только векторные иконки (drawable), системные шрифты, никаких тяжёлых анимаций,
  градиентов и больших картинок — приоритет скорость и читаемость.
* Все строки — в `strings.xml` (русский), цвета — в `colors.xml`,
  темы — в `themes.xml`.

## 7. Профиль и настройки

Экран `SettingsActivity` показывает имя, телефон, почту и статус
«пароль задан / не задан» и позволяет:

* изменить имя, почту и телефон — `PATCH /api/me`
  (`{ displayName, email, phone }`); телефон нормализует сервер, занятая почта и
  занятый телефон показываются понятными текстами (`email_taken`, `phone_taken`),
  пустое поле телефона очищает значение;
* задать или сменить пароль — `POST /api/me/password`; при `hasPassword: true`
  диалог сначала спрашивает текущий пароль, новый — не короче 8 символов;
* видит пояснение: «Укажите почту или телефон и задайте пароль — после этого
  сможете входить в веб-версию»;
* выйти из аккаунта — как раньше, с предупреждением про локальные данные и
  неотправленные черновики.

## 8. Устройства кампании (админ)

Экран приглашений разделён переключателем **«Приглашения» / «Устройства»**:

* **Приглашение участнику** — как раньше: роль, привязка к герою, срок (по
  умолчанию 168 ч), число использований → `POST /api/campaigns/{id}/invites`.
* **Регистрация устройства** — имя игрока (обязательно), роль, привязка к герою,
  срок (по умолчанию 24 ч) и подпись устройства →
  `POST /api/campaigns/{id}/devices/enrollments`. В ответ приходит
  `qrPngBase64`, код и `deepLink`; QR показывается поверх списка.
* Раздел «Устройства» — `GET /api/campaigns/{id}/devices`: имя, подпись,
  платформа, дата последнего входа и кнопка «Отозвать»
  (`DELETE /api/campaigns/{id}/devices/{deviceId}`) с подтверждением. Отзыв гасит
  сессии телефона, но не исключает человека из кампании.

Право на управление — `members.manage` (см. `docs/roles.md`).

## 9. Офлайн-режим

Локальная база (Room) — единственный источник данных для интерфейса. Сеть меняет
её двумя путями: прямыми запросами (список кампаний, участники, приглашения,
справочные выборки) и движком синхронизации `SyncEngine`.

Правки объектов и пересказов всегда локальные:

1. запись сразу попадает в Room, объект помечается `dirty = 1`;
2. в `pending_changes` добавляется запись с `base_revision` объекта;
3. `SyncScheduler` ставит отложенный воркер (debounce 3 с).

`SyncEngine` выполняет цикл из `docs/sync.md` строго в порядке **push → pull**:

* `POST /api/campaigns/{id}/sync/changes` — очередь уходит по возрастанию `seq`,
  каждая правка несёт `clientChangeId` (ключ идемпотентности);
* `APPLIED` / `CONFLICT_RESOLVED` — правка снимается с очереди, объект помечается
  чистым; `REJECTED` — снимается с очереди, состояние сервера сохраняется в
  `conflict_json`, интерфейс показывает «есть расхождение» и предлагает выбрать
  свою версию или серверную;
* `GET /api/campaigns/{id}/sync/changes?since=…` — журнал применяется к базе,
  при `hasMore = true` запрос повторяется;
* `410 resync_required` (журнал скомпактился) — полная перезагрузка через
  `GET /sync/snapshot` с курсорами.

Черновики пересказов **не покидают устройство**: пока пользователь не нажал
«Опубликовать», текст живёт в таблице `retelling_drafts` и не попадает ни в
`pending_changes`, ни в push.

Ссылки `[[Имя]]`, `[[Имя|подпись]]`, `[[#uuid|подпись]]` разрешаются **по
локальной базе** (те же правила, что у сервера).

Когда запускается синхронизация:

| Событие | Реализация |
|---|---|
| Старт приложения | `App.onCreate` → `SyncEngine.syncAll()` в фоне |
| Появление сети | `WorkManager`, `NetworkType.CONNECTED` |
| Локальная правка | отложенный воркер, debounce 3 с |
| Вручную | pull-to-refresh в списках, «Синхронизировать сейчас» в настройках |
| Периодически | периодический воркер раз в 15 минут |

## 10. Роли и права

Права приходят от сервера в `myPermissions` и проверяются на клиенте только для
того, чтобы не показывать недоступные действия (`ui/common/Rights.java`,
матрица — `../docs/roles.md`). Решение всё равно принимает сервер.

## 11. Тестовый обход

1. Запустить сервер (контур `test`, порт 8081) и указать его в `DND_SERVER_URL`.
2. Собрать и установить приложение. На экране QR нет сессии — нажать «У меня уже
   есть аккаунт» и зарегистрироваться (или войти).
3. В кампании выпустить QR устройства (Приглашения → «Регистрация устройства»),
   отсканировать его вторым телефоном: игрок входит без пароля, в профиле задаёт
   почту и пароль.
4. Создать героя и НПС — оба видны во вкладке «Персонажи» с разными подписями;
   ввести в фильтр часть имени и метку: список сужается, показывается «Найдено: N».
5. Включить авиарежим, поправить объект и создать пересказ-черновик — интерфейс
   продолжает работать, в шапке «Нет сети — работаем офлайн».
6. Выключить авиарежим, дождаться синхронизации — правки уходят на сервер,
   черновик остаётся на устройстве до нажатия «Опубликовать».
7. Отозвать устройство в разделе «Устройства»: на телефоне игрока при первой
   удачной попытке синхронизации очищается сессия и открывается экран QR с
   сообщением «Доступ отозван мастером — попросите новый QR-код».

## 12. Известные отклонения и точки внимания

* **Хранилище токенов.** В `app/build.gradle` объявлена зависимость
  `androidx.datastore:datastore-preferences:1.0.0`, но `SessionStore` использует
  закрытый файл `SharedPreferences`. Причина: Java-API DataStore работает только
  через coroutine-interop (`BuildersKt.runBlocking`, `FlowKt.first`), который
  нельзя проверить без компилятора, а доступ к токену нужен синхронно в
  `AuthInterceptor`. Перевести хранилище на DataStore можно, заменив реализацию
  одного класса.
* **Загрузка изображений в офлайне** не реализована — как и указано в
  `docs/architecture.md`, раздел 7. Эндпоинт `POST /api/files` объявлен в
  `ApiService`, но UI прикрепления картинки нет.
* **Push-уведомлений нет** (осознанно, `docs/architecture.md`, раздел 7).
* **Приглашение участника без сессии.** Контракт предписывает «сессии нет →
  `enroll`», но `POST /api/devices/enroll` принимает только токены `mode: DEVICE`
  (`DeviceService.enroll`). Поэтому приложение пробует `enroll`, а при отказе
  показывает «Это приглашение для участника: войдите в аккаунт или
  зарегистрируйтесь» и ведёт на `AuthActivity`. Полностью гладко этот случай
  пройдёт, если сервер начнёт принимать `MEMBER`-токены в `enroll` (тогда аккаунт
  создастся автоматически) или если `accept` научится создавать аккаунт по имени
  из приглашения.
* `gradle/wrapper/gradle-wrapper.jar` — настоящий jar обёртки Gradle 8.5.
