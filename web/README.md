# DnD Memory — веб-версия (PWA)

Клиентская SPA справочника настольной сессии D&D: герои, персонажи, локации,
предметы, пересказы сессий и живая навигация по упоминаниям `[[Имя]]`.
Работает офлайн: данные лежат в IndexedDB, локальные правки уходят на сервер
при появлении сети.

Контракт — `../docs/api.md` (v2), `../docs/sync.md`, `../docs/roles.md`,
`../docs/architecture.md` (раздел 4). Решения переработки — `../docs/redesign-v2.md`.

```bash
npm install       # установка зависимостей
npm run dev       # дев-сервер Vite (http://localhost:5173)
npm run build     # проверка типов + продакшн-сборка в dist/
```

Сборка — статические файлы в `dist/`, их раздаёт nginx из docker-compose
(`docker/compose.prod.yml`). Для дев-режима без отдельного домена есть прокси:
запросы `/api` уходят на `VITE_DEV_PROXY_TARGET` (по умолчанию
`http://localhost:8080`).

## Какая версия Node нужна

**Node 20 или новее** (проверено на 20 и 24). Версия зафиксирована в `package.json`
(`engines`) и в `.npmrc` (`engine-strict=true`), поэтому npm откажется ставить
зависимости на старом Node и скажет прямо, чего не хватает.

Проверить:

```bash
node -v      # v20.x или выше
npm -v       # 10.x или выше
```

Если видите `v16.x`/`v18.x`, установка не пройдёт — и это лучше, чем ошибка на
сборке. Симптом старого Node при запуске сборки:

```
SyntaxError: The requested module 'node:fs/promises'
does not provide an export named 'constants'
```

Это сообщение выдаёт сам Vite 6, а не код проекта: `fs/promises.constants`
появился в Node 20.

Как обновить:

```bash
# вариант 1: nvm (macOS/Linux) — в папке проекта есть .nvmrc
nvm install 20 && nvm use 20

# вариант 2: nvm-windows (в PowerShell/cmd)
nvm install 20.11.0
nvm use 20.11.0

# вариант 3: установщик с nodejs.org — взять LTS (20 или 22)
```

После смены версии пересоберите зависимости, затем сборку:

```bash
rm -rf node_modules      # в cmd: rmdir /s /q node_modules
npm ci
npm run build
```

## Если npm смотрит в корпоративное зеркало

На рабочих машинах npm часто настроен на Nexus/Artifactory, который знает не все
пакеты. Тогда `npm install` падает с `404 Not Found` и `… is not in the npm registry`,
хотя нужный пакет в официальном реестре есть.

В проекте уже лежит [`web/.npmrc`](.npmrc) с официальным реестром. Он перекрывает
`~/.npmrc` и `/etc/npmrc`, ничего не меняя в системе, — ровно как
`.mvn/settings.xml` для Maven.

Проверить, что применятся именно он:

```bash
npm config get registry        # https://registry.npmjs.org/
```

Если всё равно печатает зеркало, значит реестр подменён переменной окружения — она
сильнее файла:

```bash
echo "$npm_config_registry $NPM_CONFIG_REGISTRY"
unset npm_config_registry NPM_CONFIG_REGISTRY
```

Разово, без правки настроек: `npm install --registry=https://registry.npmjs.org/`.

`package-lock.json` в проекте уже указывает на `registry.npmjs.org`, так что версии
пакетов и контрольные суммы берутся оттуда же, откуда и настройка.

только в `src/api`.

## Вход, регистрация и сброс пароля

* Вход — **только по логину и паролю**. Провайдеров (Яндекс, VK), режима
  «регистрация устройства» и эндпоинтов `/api/devices/*` больше нет.
* Регистрация: логин (`3–32` символа из `a–z`, `0–9`, `_`, `.`, `-`), почта
  (обязательна — контакт для сброса пароля), пароль (от 8 символов), имя.
* `POST /api/auth/password-reset/request` отвечает `202` **всегда**, поэтому
  интерфейс показывает нейтральное «если адрес есть, ссылка отправлена
  администратору сервера». Почтовый сервер пока не подключён: ссылку
  администратор берёт из лога сервера и админ-панели
  (`GET /api/admin/password-resets`), а пользователь открывает
  `#/reset/<token>`.
* `POST /api/auth/password-reset/confirm` меняет пароль и гасит все сессии;
  неизвестный или просроченный токен приходит как `409 reset_invalid`.
* Ошибки `409 login_taken`, `409 email_taken`, `401 unauthorized` показываются
  понятным текстом на форме.

## Приглашения

`POST /api/campaigns/{id}/invites` (право `invite.create`) принимает
`{role, linkedHeroId?, expiresInHours?}`. Приглашение **строго одноразовое**:
`maxUses` всегда 1 и в запросе не передаётся, срок по умолчанию 7 дней.

Страница `/join/:token` сначала запрашивает публичный предпросмотр
`GET /api/invites/{token}` (без авторизации) и показывает кампанию, роль,
привязанного героя и срок. Дальше:

* не авторизован — либо регистрация с `inviteToken` в `POST /api/auth/register`
  (пользователь создаётся и сразу становится участником), либо вход и
  `POST /api/invites/{token}/accept`;
* авторизован — кнопка «Присоединиться» сразу вызывает `accept`.

Повторная попытка даёт `409 invite_invalid` — интерфейс объясняет, что
приглашение уже использовано или просрочено, и прячет формы.

## Профиль

`/settings` показывает логин **только для чтения** и позволяет изменить имя,
почту (обязательна, нужна для сброса пароля) и телефон (необязателен, уникален).
Почта и телефон сохраняются через `PATCH /api/me`, занятые значения приходят как
`409 email_taken` / `409 phone_taken`. Пароль меняет `POST /api/me/password`
(текущий пароль обязателен). Упоминаний устройств и входа по QR устройства нет.

## Вкладки, поиск и разделы кампании

* Четыре класса объектов (`api.md` §6) и **три вкладки**: **Персонажи** —
  герои (`HERO`) и НПС (`CHARACTER`), **Локации**, **Предметы**.
* Загрузка вкладки — два источника: IndexedDB (`[campaignId, objectType]`) и
  сервер. Герои и персонажи приходят **двумя запросами**
  (`GET .../heroes` и `GET .../characters`), локации и предметы — своими
  (`GET .../locations`, `GET .../items`). Поэтому список открывается и без сети;
  серверные данные подтягиваются поверх, но не перетирают записи с
  неотправленными правками.
* Ответ сервера разбирается **постранично** (`limit=500`, `offset += items.length`),
  пока не собраны все `total`; предохранитель — 20 страниц на класс (10 000
  объектов). Локальный список показывается сразу, страницы применяются по мере
  поступления, а рядом с «Найдено» появляется ненавязчивый индикатор
  «Подгружаем: N из M» (маленький спиннер, экран не блокируется).
* **Живой фильтр** над списком каждой вкладки: ввод с задержкой 200 мс,
  регистронезависимо по названию и описанию, у персонажа — ещё по расе и
  краткому описанию; целиком по локальной базе. Рядом «Найдено N» и очистка.
* **Пересказы** и **Участники** вынесены из вкладок в пункты меню кампании;
  их маршруты (`/campaigns/:id/retellings`, `/campaigns/:id/members`) сохранены.
  `GET /api/campaigns/{id}` отдаёт краткие `members` и `retellings`, поэтому
  участники и список пересказов открываются без отдельных запросов.
* Старые адреса вкладок героев и НПС (`/campaigns/:id/heroes`, `/npcs`) ведут на
  объединённую вкладку «Персонажи».

## Карточки объектов

Вместо `attrs` — настоящие поля класса:

| Класс | Свои поля |
|---|---|
| Герой | `race`, `klass`, `playerUserId` (игрок из участников), `items` — котомка: `name`, необязательный `itemId` (если имя нашлось среди предметов кампании), `quantity`, `notes` |
| Персонаж (НПС) | `race`, `shortDescription` |
| Локация | своих полей нет |
| Предмет | `ownerName` (владелец «как написано в мире») и не более одной ссылки: `ownerHeroId` или `ownerCharacterId` |

Права: героев создаёт, правит и удаляет **только владелец кампании**
(`hero.write`) — остальным кнопки не показываются; персонажей, локации и
предметы — владелец, мастер и игрок (`entity.write`); читают все, включая гостя
(`docs/roles.md`).

## Поиск

`GET /api/campaigns/{id}/search?q=&kinds=HERO,CHARACTER,LOCATION,ITEM,RETELLING&limit=`
ищет по `name` и `description`, у персонажа — ещё по `race` и `shortDescription`,
у пересказов — по заголовку и тексту. В интерфейсе виды подписаны понятно
(«Герои», «Персонажи», «Локации», «Предметы», «Пересказы») и снимаются
чекбоксами. Офлайн поиск идёт по локальной базе (`db/search.ts`) с той же
логикой, поэтому результаты есть и без сети.

## Оформление

Тёмная тема — спокойная тёплая палитра (тёмно-коричневые фоны, янтарный акцент),
светлая — «пергаментная». Стили без тяжёлых анимаций и крупных изображений:
приоритет — скорость загрузки и читаемость списков.

## Офлайн-режим

### Схема локальной базы (`docs/sync.md` §5)

| Хранилище | Ключ | Содержимое |
|---|---|---|
| `objects` | `id` | объекты четырёх классов: общие поля плюс поля своего класса, `objectType`, `dirty` (0/1) и `conflict` |
| `retellings` | `id` | опубликованные пересказы (только `PUBLISHED`) |
| `retelling_drafts` | `id` | черновики пересказов, **только на устройстве** |
| `pending_changes` | `clientChangeId` | очередь неотправленных правок (`objectType`, `baseRevision`, `payload`, `attempts`) |
| `sync_state` | `campaignId` | `lastPulledRevision`, `lastSyncAt`, `lastError`, признак загрузки snapshot |
| `members` | `id` | участники и их роли (кэш для офлайна) |
| `campaign` | `id` | карточка кампании: роль, права, счётчики, ревизия, краткие `members` и `retellings` |
| `meta` | `key` | служебные значения |

Схема v2 (версия базы 2) заменила прежнее хранилище `entities`: у класса своя
запись с дискриминатором `objectType` и индексом `[campaignId, objectType]`, поэтому
список одного класса читается без полного перебора. При обновлении с v1 старое
хранилище удаляется.

### Цикл синхронизации

1. **PUSH** — `POST /api/campaigns/{id}/sync/changes` с телом
   `{ clientId, changes: [...] }`. `objectType` — конкретный класс (`HERO`,
   `CHARACTER`, `LOCATION`, `ITEM`, `RETELLING`, `CAMPAIGN`, `MEMBER`), а
   `payload` — объект в форме DTO своего класса; для `DELETE` уходит надгробие
   `{ id, objectType, deleted, updatedAt }`. Локальные правки схлопываются по
   объекту (payload — полное состояние), `clientChangeId` — ключ идемпотентности.
2. **PULL** — `GET .../sync/changes?since={lastPulledRevision}&limit=500`;
   при `hasMore: true` запрос повторяется. Изменения по объектам с
   неотправленными локальными правками не применяются: локальная версия уйдёт
   на сервер следующим push. Ответ `matched_by_name` (у персонажа
   `matched_by_name_and_race`) означает, что сервер нашёл объект по ключу
   сопоставления: клиент переносит локальную запись на серверный `objectId`.
3. **SNAPSHOT** — `GET .../sync/snapshot?limit=&cursor=` при первом входе на
   устройстве и при `410 resync_required`. Страницы идут по классам (герои,
   персонажи, локации, предметы, пересказы), клиент проходит по курсорам, затем
   сохраняет `lastPulledRevision` и удаляет локальные записи, которых нет в
   снапшоте (кроме «грязных»).

### Конфликты

| `status` | Что делает клиент |
|---|---|
| `APPLIED` | снимает `dirty`, сохраняет серверную ревизию |
| `CONFLICT_RESOLVED` | то же + уведомление «ваша версия новее…» и перенос на серверный `objectId` |
| `REJECTED` | убирает правку из очереди, сохраняет `conflict.server` и показывает баннер с выбором: «оставить серверную версию» или «перезаписать своей» |

### Когда запускается

Старт приложения, событие `online`, отложенный запуск через 3 секунды после
локальной правки, кнопка «Синхронизировать» в шапке (индикатор состояния),
таймер раз в 5 минут при открытой вкладке — таблица из `docs/sync.md` §6.

### Черновики пересказов

Черновик живёт в `retelling_drafts` и не попадает ни в `pending_changes`, ни в
push. Кнопка «Опубликовать» переводит его в `PUBLISHED`: запись переезжает в
`retellings` с `dirty = 1` и уходит в очередь как `UPSERT` с `objectType:
"RETELLING"`. В интерфейсе черновики помечены бейджем «Черновик» и существуют
только на том устройстве, где созданы.

## Разметка описаний

Поддерживается markdown и ссылки `[[Имя]]`, `[[Имя|подпись]]`,
`[[#uuid|подпись]]`. Имена разрешаются по локальной базе кампании (все четыре
класса) без учёта регистра, при неоднозначности — первый по алфавиту, как на
сервере. Клик по разрешённой ссылке открывает карточку объекта, неразрешённая
рисуется пунктиром и предлагает создать объект с таким именем. HTML проходит
через DOMPurify, разметка из данных не может внедрить скрипт.

## PWA

`vite-plugin-pwa` собирает манифест (имя «DnD Memory», тёмная тема, иконки SVG,
включая maskable) и service worker: app shell кэшируется, поэтому приложение
открывается без сети, а данные приходят из IndexedDB. Изображения объектов
(`/api/files/...`) кэшируются стратегией stale-while-revalidate.

## Права

Интерфейс опирается на `myPermissions` из `GET /api/campaigns/{id}`, а при
отсутствии связи — на локальное зеркало матрицы ролей из `docs/roles.md`
(`src/utils/permissions.ts`). Сервер остаётся источником истины: он проверяет
права при каждой записи, клиент лишь не показывает недоступные действия.
Героев ведёт только владелец кампании, поэтому даже push героя от игрока сервер
отклоняет с `REJECTED` / `forbidden`.
